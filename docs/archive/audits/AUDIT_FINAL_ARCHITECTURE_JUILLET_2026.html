Points Faibles — Ce qui doit être corrigé
Problèmes réels identifiés — sans minimiser leur impact
🔴
CRITIQUE — 0 client, 0 revenu, 0 VPS algérien
Le code est parfait mais personne ne l'utilise. Le serveur est aux USA (Railway) → non-conforme loi 18-07 → impossible de mettre de vraies données élèves. C'est le problème #1. Tout le reste est secondaire.
🔴
CRITIQUE — Frontend inaccessible (CORS/Railway)
Vercel affiche "Impossible de joindre le serveur". Un prospect qui visite le site aujourd'hui repart. C'est 30 minutes à corriger (VITE_API_URL + CORS_ALLOWED_ORIGINS) mais ça n'a pas encore été fait.
🟠
IMPORTANT — Trop complexe pour un dev solo en maintenance
6 niveaux de sécurité, Merkle Chain, SIEM, Post-Quantum... Si tu tombes malade ou travailles sur autre chose 2 mois, qui maintient ça ? La complexité est un actif mais aussi une dette.
🟠
IMPORTANT — Satim uniquement en sandbox
Les paiements CIB/Dahabia pointent vers test.satim.dz. Les démarches bancaires en Algérie prennent 4-8 semaines. Sans ça, les paiements en ligne ne fonctionnent pas en vrai.
🟠
IMPORTANT — Marketplace non finalisée
Le code existe mais la fonctionnalité est incomplète et désactivée par défaut. C'est potentiellement la plus grande source de revenus (commissions sur transactions) mais elle n'est pas prête.
🟠
IMPORTANT — Pas de monitoring en production
Sentry est configuré mais le DSN n'est pas encore renseigné. Si le serveur tombe en production, tu le sais quand le client appelle. UptimeRobot non configuré non plus.
🟡
MODÉRÉ — Pas de plan d'onboarding client
Quand un directeur d'école signe, comment l'accompagnes-tu ? Tutoriel vidéo ? Formation ? Plan d'onboarding ? Rien de ça n'existe encore. La documentation technique est là mais pas le guide pratique.
🟡
MODÉRÉ — Tests de charge absents
724 tests fonctionnels mais 0 test de performance. Que se passe-t-il quand 50 écoles se connectent simultanément ? Inconnu. Les index PostgreSQL sont là mais la charge réelle n'a jamais été simulée.

Améliorations Techniques Restantes
Ce qui pourrait encore être amélioré — par ordre de priorité
  • 1
    Tests de charge — k6 ou Artillery
    Simuler 50 schools connectées simultanément. Valider que les index PostgreSQL tiennent la charge. Identifier les goulets d'étranglement avant la mise en production.
  • 2
    CI PostgreSQL pur — Supprimer toute compat SQLite
    L'historique montre des "jsonb→json" pour SQLite. Configurer le CI pour rejeter toute migration non compatible PostgreSQL. Un test qui passe sur SQLite mais échoue en prod est dangereux.
  • 3
    Intégration React Native — Tests automatisés Detox
    18 écrans mobiles mais 0 test E2E. Les régressions mobiles sont invisibles. Ajouter au moins des tests Jest sur les composants critiques (paiement, notes).
  • 4
    Secrets GitHub — Déplacer les credentials du CI
    DB_PASSWORD visible dans ci.yml. Pas un risque critique (credentials de test) mais mauvaise pratique. Déplacer vers GitHub Secrets : ${{ secrets.TEST_DB_PASSWORD }}.
  • 5
    Analytics dashboard — Pour les directeurs
    Rapport mensuel automatique envoyé par email (PDF) : CA, absences, moyennes, tendances. Les directeurs adorent les chiffres sans avoir à chercher dans l'interface.
  • 6
    Notifications email — Actuellement que SMS/Push
    Laravel Mail est configuré mais peu utilisé. Les parents qui n'ont pas installé l'app reçoivent des SMS. Un email HTML soigné (bulletins, convocations) renforcerait le professionnalisme.
  • 7
    Mode hors-ligne Progressive Web App
    Les écoles algériennes ont parfois une connexion instable. Un mode hors-ligne pour la saisie des présences (sync quand connexion retrouvée) serait un vrai différenciateur.
  • 8
    IA — Prédiction échec scolaire (au-delà EWS)
    Le diagnostic EWS existe avec du scoring basé sur des règles. Intégrer un modèle ML simple (régression logistique) entraîné sur les données agrégées pour prédire les risques à J+30.
